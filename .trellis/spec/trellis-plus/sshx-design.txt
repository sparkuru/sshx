SSHX：跨平台 SSH 会话框架与独立插件系统
项目设计与实施 Prompt

一、任务与需求来源

你负责设计并逐步实现一个跨平台 SSH 增强框架，暂用 SSHX 作为代号。
先形成可验证的架构和技术验证计划，再实施最小可运行版本。所有结论必须区分已验证行为、设计决定和待验证假设。不要一次性生成没有运行证据的大型代码骨架。

本需求由六轮讨论演进而来，最终意图如下：
1. 起点是在本地截图后，将剪贴板图片上传到当前 SSH 目标，并把远端路径插入输入位置。
2. 曾考虑类似 PicGo 的托盘工具，但识别活动终端、标签页和 SSH 目标会引入不可靠的推断，因此不作为核心方案。
3. 明确采用独立命令：ssh target 保持原样，sshx target 提供增强功能。不得覆盖 ssh、修改其别名或透明接管已有 SSH 进程。
4. 产品扩大为本地 C/S 框架，负责连接、管理、会话识别和多会话切换；图片、文件传输、命令历史、命令参考、端口转发等由插件实现。
5. 讨论推荐 Rust 核心和语言无关协议。本稿以 Rust 为默认技术路线；这是选型基线，不冒充用户已经明确指定语言。只有实证发现阻碍时才提出替代方案。
6. 最后明确：所有业务插件都独立开发、构建、运行和发布。官方仅维护并默认分发其中一部分，与社区插件使用相同公开接口和权限模型。

本稿合并上述意图，并补充工程边界。此前的“先内置插件，后开放外部插件”“官方插件直接调用 Core 内部 Trait”等建议全部废弃。官方插件可以与核心放在同一仓库，但不得链接进 Core 或依赖 Core 私有实现。

sshx 已被其他项目使用，本稿只把它当设计代号。正式发布前另行确认名称和命令冲突，不在本任务中自行改名。[已有 sshx 项目](https://github.com/ekzhang/sshx)

二、产品边界与使用方式

主要面向 CLI/TUI。可参考 MobaXterm、WindTerm、VS Code Remote SSH 的工作流，不复制大型 GUI、云账户或完整远程开发平台。

客户端目标：Windows、Linux、macOS。测试必须区分操作系统、终端宿主、Shell 与显示系统。PowerShell 是 Shell，Windows Terminal 是终端宿主；Linux 需分别记录 X11、Wayland 和无图形会话。
远端目标：Linux、macOS、Windows 上的标准 SSH 服务。基础登录不要求 SFTP；图片和文件传输要求对应目标确实提供 SFTP 能力。基础功能不安装远端 Agent。

预期命令示例：
  ssh target
  sshx target
  sshx -p 2222 -i ~/.ssh/id_ed25519 -J bastion target
  sshx connect -- target
  sshx session list
  sshx session attach <session-id>
  sshx session detach <session-id>
  sshx session close <session-id>
  sshx plugin list
  sshx plugin enable <plugin-id>
  sshx plugin disable <plugin-id>
  sshx plugin install <local-package>
  sshx plugin uninstall <plugin-id>

使用显式 connect 命令消除目标名与管理子命令冲突。确定并记录参数解析、-- 分隔符、未知参数和远端命令的行为。上述是待实现的接口要求，不是已有软件的命令声明。

交互式登录是增强模式的优先支持范围。对于管道、重定向、远端命令、-T、-N、-W、子系统、后台化等模式，逐项选择原生透传或明确拒绝增强模式，不得一律套 PTY，不得把二进制输出和 stderr 合并污染。透传模式可以不创建受管理会话，但要说明原因和差异。禁止默默丢弃 SSH 参数。

复用系统 OpenSSH 的配置、known_hosts、身份文件、ssh-agent 和跳板配置；身份校验继续交给 OpenSSH。参数用 argv 传递，不拼接本地 Shell 命令。远端命令仍遵循 OpenSSH 自身语义，不声称本地 argv 可以消除所有远端 Shell 解析。[OpenSSH ssh 手册](https://man.openbsd.org/ssh.1)

三、固定架构与组件职责

这里的 C/S 指本机 Client 与用户级 Core Service。远端 SSH Server 是另一层，SSHX Agent 只是可选增强组件。

  本地终端
     |
  CLI/TUI Client —— 桌面剪贴板适配器
     | 用户级本地 IPC
  Core Service
     ├─ Session Manager / 输入所有权 / 生命周期
     ├─ PTY 或 ConPTY / OpenSSH 子进程
     ├─ Transport Broker / SFTP / 转发资源
     ├─ Plugin Manager / RPC / Capability 授权
     └─ 结构化事件 / 有界缓冲 / 运行状态
           | stdio RPC
           ├─ Image Paste 独立进程
           ├─ File Transfer 独立进程
           └─ 其他官方或社区插件进程

  OpenSSH ── SSH ── 远端 SSH Server
                         └─ 按需 Shell Hook / 可选 Agent

Client：
- 负责终端输入、显示、快捷键、菜单、通知和桌面能力。
- 在当前登录桌面会话内访问剪贴板；Core 将请求定向到触发操作的 Client。不得依赖后台服务拥有 DISPLAY、Wayland 或 macOS 桌面权限。
- 进度和日志留在本地界面，不写入远端 Shell 输入流。

Core：
- 按需启动的非特权用户级服务，从首个 C/S 垂直切片开始拥有 SSH 子进程和 PTY。
- 多个 Client 可连接同一 Core，但“活动会话”属于具体 Client/Attachment，不设全局唯一 active_session。
- 管理会话、认证交互通道、传输、插件和资源；不包含图片命名策略、历史检索或命令示例等业务。
- 为插件提供可审计的公开能力；不向插件暴露任意进程执行器、裸 PTY 句柄或内部服务注册表。
- 定义并发启动锁、旧端点识别、协议版本不兼容、空闲退出和服务升级行为。升级不得无提示中断活跃会话。
- 创建会话时显式传入必要的工作目录和环境上下文；避免所有会话误用第一次启动 Daemon 时的 SSH_AUTH_SOCK 或桌面环境。对环境变量采用允许列表，不把完整环境交给插件。

Core 提供文件传输和转发机制，插件提供操作策略、配置与 UI。Core 提供快捷键分发和动作注册，插件声明动作，不必获得全部键盘输入。
Core 提供剪贴板访问代理，Image Paste 决定编码、文件命名与输出格式。Core 提供结构化 Shell 集成事件，History 决定记录、查询与保留策略。

四、会话模型与终端兼容性

至少区分以下对象，并给出字段、所有权、状态转换和清理规则：
- ConnectionProfile：原始目标、必要连接参数、配置来源和配置版本。不能仅凭 hostname 合并身份。
- Session：唯一 session_id、连接代次 generation、所属 Profile、进程状态及能力集合。
- Attachment：client_id、attachment_id、所属 Session、窗口大小和输入所有权。
- Operation：operation_id、发起插件、Session/generation、发起 Attachment、状态、取消与结果。
- TransportHandle：文件传输或转发资源；与会话绑定，但未必共用同一 TCP 连接。
- CapabilityGrant：插件实例、操作、会话或路径范围、有效期和撤销状态。
- RemoteContext：目标、Shell、cwd、路径命名空间及其来源、更新时间、可信程度。

采用单写者会话模型。首版每个会话只允许一个交互 Attachment；争用返回明确错误。后续如支持只读观看或接管，必须单独定义授权及通知。窗口大小由当前写者决定。
切换会话撤销旧 Attachment 的输入权；异步插件结果必须携带最初的 Session、generation 和 Attachment 绑定，不得重新查询“当前活动会话”后投递。

终端数据按字节处理，不能对每个读取块单独做有损 UTF-8 解码。控制面、终端流、插件 RPC、文件数据分流；所有队列有容量和溢出策略，慢插件不得阻塞 SSH。
验证 ANSI/VT、中文与输入法、Ctrl+C、Ctrl+D、Unix 作业控制、窗口缩放、粘贴模式、密码与 MFA、全屏程序和退出码。正常退出和可捕获异常应恢复终端状态；不可捕获终止提供恢复说明。
保留 OpenSSH 自身的转义交互，给 SSHX 前缀键设计禁用与字面透传方式。不要把本地收到的 Ctrl+C、发送字节 0x03、子进程信号和远端信号混为同一个动作。
Windows ConPTY 需要实际验证进程创建、I/O、窗口调整和关闭时序，不能以 Unix 测试替代。[Microsoft ConPTY 文档](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session)

Attach/Detach 必须拆成三个问题：
1. Client 分离后，本地 Core/PTY/OpenSSH 是否仍存活。
2. 再次附着时，终端屏幕、光标、模式和全屏程序如何恢复。
3. 网络断线、Core 崩溃或本机重启后，远端工作是否仍能恢复。

后台进程存活不代表屏幕可恢复；原始字节日志不能直接作为安全可靠的屏幕快照，无界回放还可能重新触发剪贴板等控制序列。Phase 0 比较有界 VT 状态模型与受限重绘方案，公布支持的终端模式。完整切换与附着验收应覆盖备用屏幕、resize 和 Vim。
Core 崩溃后不承诺收养遗留 PTY；网络重连创建新的 generation，旧操作和输入授权失效。远端进程恢复可选依赖 tmux 等远端能力或后续 Agent，不作为纯本地框架的默认保证。
持久化的会话元数据不等于存活会话。定义显式 detach、关闭 Client、Client 意外退出、退出远端 Shell、服务停止各自的保留和清理策略。

五、SSH 与文件传输的复用边界

必须分别描述配置复用、认证身份复用、SSH 网络连接复用。
优先在已验证环境使用 OpenSSH 连接复用。ControlMaster 等能力按实际客户端版本与平台探测，不能把 Unix 结果推广到 Windows，也不写永不过时的平台绝对结论。
不能复用时，Core 创建同目标的辅助传输连接。此时可能再次触发密码、MFA 或硬件密钥交互，不能声称天然免认证。

传输后端在 Phase 0 比较：
A. 系统 sftp 子进程，适合快速验证，但要明确批处理、命令转义、取消、进度和错误解析边界。
B. 系统 ssh 启动 SFTP 子系统，通过管道使用成熟 SFTP 协议库。继续复用 OpenSSH 认证与配置，不自研 SSH 协议栈。
选择一个能完成 MVP 的后端并记录依据，不同时构建两套完整实现。
系统 sftp 批处理没有交互能力，应配合非交互认证；不能在批处理卡住后偷偷借主 Shell 终端收密码。[OpenSSH sftp 手册](https://man.openbsd.org/sftp.1)

基础登录必须支持系统 OpenSSH 可用的交互认证。MVP 传输可先支持 agent/key 或有效复用连接；需要额外交互认证时返回 AUTH_REQUIRED，明确列入尚未支持项。后续实现专属、用户可见的认证流程，插件不得读取凭据，不缓存或重放主连接密码。
辅助连接只继承适用的连接选项；不重复执行 RemoteCommand、不重复创建原有转发，不强行携带 RequestTTY。验证 -F、-p/-P、-i、-J、ProxyCommand 和 -o 等参数映射。
配置变化后不得把旧会话的上传静默转向新目标。为传输绑定配置代次及可验证的目标信息；无法确认时拒绝或要求重新选择。不要依赖解析窗口标题或远端提示符。

SFTP 路径与 Shell 路径分开建模。Windows、SFTP chroot、远端容器等场景中，两者不一定相同。不能用本地 Path API 解释远端路径，不能假定 ~ 自动展开。
默认上传位置使用经 SFTP 确认的用户目录下专用子目录；不把 SFTP 初始目录当远端 Shell 当前目录。不支持自动映射时允许配置并验证映射，无法验证则只提供传输路径，不伪称可用于 Shell。

六、全独立插件规范

从第一个 Image Paste 插件起即使用独立进程和公开协议。禁用或卸载全部插件后，连接、会话列表和会话管理仍可运行。
默认随包安装不等于默认授予全部能力，也不等于开启历史记录或持续监控剪贴板。

Manifest 至少包含：id、version、API 版本范围、entrypoint、参数数组、平台要求、配置 schema、命令/动作、能力申请。安装不执行任意安装脚本；MVP 接受明确路径的本地插件包，验证归档路径与入口，版本不兼容时在启动前拒绝。
生命周期：发现 → 校验 → 启动 → 握手 → ready → 调用/订阅 → 停止。启动失败、超时、崩溃和协议错误不影响 SSH 主连接。按需启动，定义重启上限，避免崩溃循环。

协议采用版本化 JSON-RPC 2.0，通过 stdin/stdout 双向通信，stderr 仅作有界日志。JSON-RPC 定义消息结构，但没有替项目选择字节流分帧、权限或版本协商。[JSON-RPC 2.0 规范](https://www.jsonrpc.org/specification)
首版统一使用 Content-Length 头和 UTF-8 JSON 正文分帧；长度按字节计算。给出头格式、最大消息长度、超时、请求 ID、并发请求、错误码和取消扩展。不得把日志混入 stdout。
插件 API 版本独立于插件版本和 Core 版本；定义初始化协商、未知方法、可选字段、向后兼容及不兼容拒绝规则。
图片和文件不以无限大的 base64 JSON 消息传递。使用绑定实例、会话和操作的短期 blob/stream 句柄；Core 控制读取、大小上限和释放。禁止把任意文件路径作为绕过文件授权的句柄。

公开能力至少覆盖：
  session.describe / action.register / event.subscribe
  clipboard.read_image / blob.read / blob.release
  transfer.upload / transfer.download / operation.cancel
  terminal.propose_insert / ui.notify
  forward.create / forward.list / forward.close
后期按需求加入结构化命令事件和插件命名空间存储。以上是待设计的协议名称，不暗示已有库 API。

Core 依据实际插件进程绑定身份，不信任请求体中自报的 plugin_id。每次能力调用在产生效果前检查实例、会话代次、路径范围、操作归属和撤销状态；停用插件时撤销授权并处理未完成操作。
默认不给插件原始终端输入输出，不广播剪贴板内容、其他会话或其他插件私有状态。原始终端流访问是高敏能力，不能依靠“识别密码提示”过滤后声称安全。

独立进程提供故障隔离，不提供操作系统沙箱。未沙箱化插件仍可能直接访问同用户文件和网络，绕过 RPC；因此首版只运行用户明确信任的本地插件，不宣称能安全执行恶意插件。
后续若支持不可信插件，必须先实现并验证各平台的文件、网络、进程和资源限制，覆盖子进程与组合能力。官方插件不获得绕过通道。

事件应包含版本、event_id、session_id、generation、operation_id（若有）、来源和序号。定义顺序范围、丢失提示及重新查询状态方式；不承诺未经实现的全局可靠事件总线。
“进程已启动”“认证已完成”“Shell 可输入”分别建模。没有可靠证据时返回 unknown，不能根据出现 $、#、> 或一段输出伪造 session.connected / command.finished。

七、Image Paste：首个端到端闭环

默认触发方式：可配置的 SSHX 前缀键加动作，例如 Ctrl+] 后按 p；同时提供显式绑定 Session 的命令入口。前缀键的冲突、取消、超时与字面透传必须可测试。
普通文本粘贴保持终端行为。终端可能预先消费 Ctrl+V、Ctrl+Shift+V 或 Command+V，CLI 不能保证收到这些按键或图片；原生粘贴快捷键属于后续终端/桌面适配，不作为通用 MVP 前提。
OSC 52 面向文本剪贴板，不作为通用图片通道；kitty OSC 5522 等图片能力只能作为按终端能力启用的扩展。[kitty 剪贴板协议](https://sw.kovidgoyal.net/kitty/clipboard/)

单次操作流程：
1. 在触发时固定 client_id、attachment_id、session_id、generation、输入所有权及目标说明。
2. 从该 Client 的桌面剪贴板读取一次快照；无图片、无桌面访问或权限不足返回明确结果，不偷偷扫描文件或发送文本。
3. Image Paste 插件将图像规范化为 PNG。验证尺寸、解码内存和编码大小上限，保留透明度；首版不必支持所有编码格式。插件只能读取本次授权的图像句柄。
4. 插件决定文件名和输出格式；默认采用时间信息加随机 ID，避免重名覆盖。Core 验证目标目录和传输权限。
5. 上传到唯一临时名，完成后在服务能力允许时 rename 到最终名。描述 rename 的覆盖和原子性限制，不把文件大小相同冒充完整哈希校验。
6. 只有传输完成并获得可用路径后，才提出插入建议。记录上传成功但插入未完成这一独立状态，重试插入不重新上传。
7. Core 再次验证会话代次、Attachment、输入权和交互上下文。目标切换、断线、分离、插件停用或授权过期时，不向当前窗口补发输入。
8. 释放临时资源；失败时只清理该操作自己创建的临时文件。取消与失败不得插入半成品路径。

路径插入规则：
- 仅写入文本，不附加 Enter、换行或控制序列。拒绝 NUL、ESC、CR/LF 等不能安全插入的内容。
- “不发送 Enter”不能保证输入无副作用，全屏应用也可能把字符当命令。用户应在目标输入位置触发动作；持续跟踪操作期间的上下文变化。
- 有受支持的 Shell/编辑器集成且上下文仍有效时允许自动插入。无集成时可使用明确的本次粘贴交互，短暂托管输入并允许取消；无法建立可靠上下文则保留结果，提供用户确认插入或复制路径，不盲目输入。
- 不把 bracketed paste 当安全沙箱。只在接收程序支持时使用，且仍执行字符与目标校验。
- 区分 Shell 参数、纯路径和 Markdown 三种输出。分别为 POSIX Shell、PowerShell、cmd 等实现并测试编码；未知 Shell 不套用 POSIX 转义。
- 不在已有引号内部盲目插入一个“已转义参数”。集成无法识别当前编辑上下文时采用预览或纯文本复制。
- 相对路径只有在已知引用基准时生成。Shell cwd 与 Markdown 文档目录可能不同；默认提供验证后的绝对 Shell 路径，缺少映射时明确说明。
- 嵌套 ssh、sudo、容器或 tmux 不能仅靠外层 Session ID识别内部目标。上传仍绑定 SSHX 管理的外层目标；检测到歧义或用户处于内部环境时显示真实目标，不声称自动追踪嵌套会话。

可配置项：上传目录、命名模板、输出模式、本地缓存策略、大小上限。MVP 默认不持续监听剪贴板、不保存长期本地图片缓存、不覆盖远端已有文件。

八、后续插件范围

File Transfer：文件上传下载、目录与批量任务、进度、取消、覆盖策略、失败重试。目录遍历、符号链接、同名文件和下载路径单独定义；重试不能造成静默覆盖。拖拽、增量同步和文件管理 TUI 后置。

History：只记录用户启用的受支持 Shell Hook 产生的结构化命令记录，字段至少有 Session、目标、用户、cwd、命令、时间及可选退出码。缺少字段使用 unknown，不从按键猜命令。Shell 标记可辅助边界识别，但不保证提供完整命令文本，需另行设计 Hook。[Shell 集成参考](https://wezterm.org/shell-integration.html)
历史是“受支持的交互 Shell 命令历史”，不声称覆盖所有子进程内部执行。默认关闭；支持会话排除、暂停、过滤、保留期限和删除。过滤发生在持久化前，注明无法保证完全脱敏。查询结果只插入，不自动执行。SQLite 数据归插件管理。

Command Reference：优先离线命令示例、按已知远端系统筛选、用户模板及检索。记录示例内容来源和许可证。历史整合需独立授权，不直接读取 History 私有数据库。首版不引入 AI 服务。

Port Forward：插件管理策略和界面，Core 管理实际资源。支持本地、远端和动态转发，明确生命周期、端口冲突、创建失败及连接状态。动态增删优先使用经过验证的复用控制能力；否则使用 Core 托管的独立 ssh -N 进程，说明额外认证和退出条件。
默认回环绑定；监听所有接口属于显式选择。不能把终端输出中的 URL 当可信命令自动开端口。远端服务发现需要明确来源和用户配置；“进程存活”“监听建立”“目标可达”分别显示。

Clipboard Bridge：面向 Vim/Neovim 等受支持环境的文本复制粘贴。区分远端写本地剪贴板和读取本地剪贴板，分别授权与限流；OSC 支持按终端、复用器和编辑器组合验证。远端输出不能自行授予本地剪贴板读取权。

Shell Hook / Agent：只在后续精确 cwd、命令历史、端口发现或编辑器集成需要时加入。比较无 Agent、按需临时进程和常驻 Agent，优先最小部署。通过 SSH 保护的独立通道通信，不默认监听公网。不在用户 Shell 配置中静默写入永久 Hook。
远端上报内容作为不可信数据，不能直接执行，也不能凭一段 OSC 获得本地权限。cwd、OS、Shell 均应包含探测来源和 freshness，允许 unknown，不向正在使用的交互 Shell 注入探测命令。

九、安全、IPC 与数据边界

威胁模型覆盖其他本地用户、恶意或失控插件、被控制的远端、伪造控制序列、路径注入、会话切换竞态和恶意插件包。说明同用户恶意进程、管理员及未沙箱化插件的防护边界。
Unix 使用受用户权限保护的运行目录与 Unix Domain Socket，并核验 peer 身份；Windows Named Pipe 配置当前用户 ACL、校验对端并限制远程访问。名称随机不替代授权。端点创建、符号链接和陈旧文件清理应避免竞态。
Client、Core 和 Plugin 三类通道角色分开；插件 stdio 连接不能转换成拥有全部权限的 Client。Core 不默认开启 TCP 管理端口。
OpenSSH 独占凭据处理。不得向插件、日志或遥测传递私钥、密码、agent 访问能力或完整环境。诊断日志默认只含必要元数据，隐藏终端正文、剪贴板和命令正文。
终端直通模式并不代表 Core 已过滤全部危险终端协议；明确哪些序列会拦截、透传及依赖宿主权限。重放时不得重复执行剪贴板、通知等有副作用的序列。
文件权限与 ACL、传输路径约束、符号链接行为、大小配额和临时文件清理需要在实际执行处检查。不能只在插件 manifest 中声明。
不默认持久化终端录屏或键盘输入。内存缓冲有上限；插件数据与 Core 会话元数据分开存储。配置采用各平台标准用户目录，不把 Unix 路径写死到所有系统。

十、技术基线与工程组织

默认采用 Rust + 系统 OpenSSH；Tokio、portable-pty、Serde/TOML、Ratatui/Crossterm、arboard、SQLite 是候选组件，不是未经验证的强制清单。
剪贴板库支持操作系统不代表支持每个桌面组合，需核实版本、构建 feature 与 Wayland 协议条件。[arboard 项目文档](https://github.com/1Password/arboard)
锁定实际验证过的依赖版本，查阅对应版本官方文档，不虚构 API。需要系统依赖时如实说明，不承诺全部平台零依赖单文件发布。核心可打包为少量可执行文件，默认插件依然独立分发。

初期目录按真实边界组织，避免每个概念都拆一个 crate：
  crates/cli/             CLI、终端前端、桌面适配
  crates/core/            服务、会话、PTY、传输、插件宿主模块
  crates/protocol/        公开 schema、类型、版本与协议测试
  plugins/image-paste/    独立可执行插件、manifest、配置
  plugins/.../           按阶段增加其他插件
  integrations/          后续 Shell/编辑器/Agent 集成
  docs/                  架构、ADR、协议、兼容性与运行说明
  tests/                 集成测试、协议夹具、平台验证记录

允许根据实际依赖拆分模块，但 Core 不能依赖任何具体插件。插件只依赖公开协议或 SDK；用一个不使用 Core 内部库的最小示例证明语言无关性。

十一、实施阶段与退出条件

Phase 0：高风险可行性验证。
- 验证 PTY/ConPTY + OpenSSH 的交互、输入输出、认证、resize 和退出清理。
- 验证用户级 Core 托管进程、本地 IPC 身份、多 Client 和单写者行为。
- 验证三平台图片剪贴板访问；Linux 单列 X11/Wayland，不可访问时给出文件选择降级。
- 验证 SFTP 后端、认证方式、特殊路径、Windows 路径映射和不支持 SFTP 的处理。
- 验证 attach 后的屏幕和模式恢复，明确受限方案与完整方案的成本。
- 验证前缀键确实能被目标终端传入；验证异步上传期间切换 Session 不会错投。
输出：每项环境、方法、结果、限制和替代方案。缺少平台测试环境标记未验证，不以交叉编译代替运行验证。

Phase 1：可运行的 C/S + 独立插件 MVP。
- sshx target 经 Client/IPC/Core 启动交互会话；Core 支持多个独立会话、列表和关闭。
- 插件发现、版本协商、启停、能力检查、事件订阅和本地包安装从此阶段具备。
- Image Paste 独立进程完成剪贴板读取、PNG、上传和有条件的安全插入；上下文不足时明确降级到保留结果。
- 插件关闭、崩溃、超时均不影响原 SSH 会话。
- 主平台完成完整垂直切片，并保留其他平台构建和明确的运行缺口；不能据此宣布全平台完成。
不把所有高级插件塞进 MVP，也不把项目降级成无法迁移到 C/S 的单进程脚本集合。

Phase 2：多会话交互与常用插件。
- 基本 TUI、切换、detach/attach、屏幕恢复和输入所有权交接。
- File Transfer、Port Forward、Command Reference。
- 补齐三客户端平台与三远端系统的代表性组合，记录认证和终端条件。

Phase 3：远端结构化集成。
- 按 Shell 分批支持 cwd、命令事件、History 和 Vim/Neovim Clipboard Bridge。
- 仅为确有需求的能力引入可选远端组件。
- 完成辅助连接的交互认证体验，扩大路径和嵌套环境支持。

Phase 4：发布与生态。
- 独立插件更新、版本回退、包完整性和发布者可信来源、SDK、跨平台包与文档。
- 不可信插件执行前完成实际沙箱隔离；不把此要求用普通 RPC 权限声明替代。
- 插件市场、WASM、云服务、GUI 和 AI 能力均非必须项。

十二、验收与故障测试

为每阶段建立需求到测试的对应关系。至少覆盖：
1. 原生 ssh 不受安装或卸载影响；卸载全部插件后，Core 仍能登录和管理会话。
2. 用户、端口、身份、跳板、配置文件和主机密钥检查与预期一致；主机密钥变化不得静默接受。
3. 文本、中文、控制键、窗口缩放、全屏程序、认证和退出行为经过实际终端验证；透传模式保留 stdout/stderr 与字节内容。
4. 同主机多个会话、不同主机多个会话、同时上传，以及 A 上传途中切换到 B，均不会把数据或输入发送到错误会话。
5. 上传期间 detach、断网、Session 关闭、generation 改变、插件禁用和权限撤销，结果都不会过期投递。
6. 图片为空、超大、损坏、权限不足、无 SFTP、重复文件名、磁盘满、半途失败和取消，能正确报告并清理所属临时资源。
7. 路径覆盖空格、中文、引号、$、反引号、分号、前导短横线、换行、Windows 盘符、SFTP 命名空间差异；不产生命令注入。
8. 上传成功但插入失败可以独立重试；重复请求有 operation_id 和去重语义，不重复创建文件或重复输入。
9. 插件错误 JSON、超长帧、握手不兼容、阻塞、崩溃、越权会话和伪造身份都被隔离；慢订阅者不阻塞终端。
10. 未授权本地用户无法接管服务；Shell Hook 或恶意远端输出无法直接触发本地剪贴板读取、文件外传或端口开放。
11. 无 Shell 集成时不生成虚假历史和退出码；关闭 History 后不再持久化；历史和临时缓存按用户设置删除。
12. Detach 后远端进程行为、再 Attach 的屏幕状态、Core 崩溃和网络重连分别测试，不用一个“重连成功”掩盖差异。

测试按风险选择：纯状态机和编码单元测试、插件协议契约测试、SSH/SFTP 集成测试，以及三平台真实终端测试。容器可辅助远端服务验证，不能替代 Windows ConPTY、桌面剪贴板或 macOS Terminal 的实测。

十三、交付顺序与完成标准

首先交付：
1. 需求清单，区分已明确决定、本文默认决定和待验证技术点。
2. 能力/平台矩阵，列出支持条件、降级方式和未知项。
3. 组件与进程图、所有权、依赖方向及主要数据流。
4. 核心数据模型、状态机、IPC 与插件协议、权限校验位置和错误语义。
5. 图片上传完整时序及失败分支，包含会话切换、取消、认证和插入上下文。
6. 关键 ADR：语言、PTY、传输后端、屏幕恢复、插件隔离和远端集成边界。
7. 分阶段任务及可执行验收方法，然后开始 Phase 0 和首个垂直切片。

设计足够支撑下一步且没有真实阻碍时继续实施，不以例行“是否继续”代替工作。涉及产品范围改变或实际无法推断的关键选择时再提出具体问题。
每阶段报告实际文件变更、构建运行方法、已执行检查、失败与尚未验证的平台。不要把规划功能写成已实现，不把架构文档当运行证据。

最终成果应实现：用户用 sshx 管理自己的 SSH 会话，通过可独立替换的插件完成图片、文件和其他增强工作；核心稳定运行，插件边界公开，跨平台能力有实测依据，失败与降级行为可理解。
