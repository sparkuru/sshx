# Proposed SSHX v1 contracts

Status: design, 2026-10-22. Nothing here is an implemented API. This is the normative home for proposed schemas, constants and errors; other documents refer here. API version 1.0 is independent of executable/package versions. [Source IV–IX](../.trellis/spec/trellis-plus/sshx-design.txt) supplies requirements; [Image Paste](image-paste.md) composes them.

## Types and binding

Ids are opaque random 128-bit values encoded as lowercase hexadecimal strings, globally qualified by core_instance_id (new on each Core boot). They are not authority by themselves. Counters/generation/offset/length are nonnegative JSON integers within the exact-integer range in Limits, never floating values. Times on the wire are RFC 3339 UTC strings; enforcement uses monotonic deadlines owned by Core. null means unknown, not false or an empty inferred value. Required fields must be present, including null where allowed. Diagnostic strings are bounded, untrusted and rendered as text.

Binding B = {core_instance_id, operation_id, session_id, generation, client_id, attachment_id, writer_epoch, profile_id, config_generation}. Core captures B from an authenticated explicit Client action and the current writer. Plugin requests for operation-scoped methods carry operation_id and, where the method table specifies them, grant_ids. Core resolves the instance's active, unexpired and unrevoked grants for every grant-requiring method, including calls without an explicit grant_ids field, and looks up the immutable B; it never trusts a supplied replacement. Handshake/registration and ownership-only methods retain their explicitly stated checks. A grant may narrow that binding, never broaden it. Operation projections and operation events carry operation_id and session_id/generation. Compact RPC results use their pending request's operation/B correlation; accepting or delivering an asynchronous result rechecks that binding, never “current active session”.

Redacted target = {profile_id, config_generation, display_label, outer_destination, verified_target_id|null}. It excludes identity paths, environment, command text and credential material. A verified_target_id is a broker-generated reference to actual tested target evidence (host identity/user/route/config binding), not a plugin self-assertion or matching hostname. Nested environments remain separate from the outer target.

## Limits

These are deliberately finite **proposals**, not measured safe defaults. User configuration may lower image/operation limits; increasing them needs a new reviewed profile. MiB/KiB use binary units. Limit exhaustion fails before allocation/effect with LIMIT_EXCEEDED unless a more specific result below applies. Aggregate budgets dominate individual maxima.

Record caps include active and retained entries unless explicitly identified as a live-resource limit. Session/Client records cannot escape their caps through exit/disconnect churn. Release unreferenced records after their retention deadline; a lost Client identity is never accepted again. Attachment tombstones exist only while referenced by a retained Operation, at most one distinct initiating tombstone per Operation; remove an unreferenced detached Attachment immediately. Thus all Attachment records are bounded by ATTACHMENT_MAX × SESSION_MAX + OPERATION_MAX as well as the metadata budget. Profiles are retained only for their capped Sessions/Operations. Grants, including revoked/expired records still needed for an in-flight check, count toward GRANT_MAX; renewal updates the same owned record, never appends an unbounded history. Unneeded expired/revoked grants are released. Unexpired operation/result records and live resources cannot be evicted to make admission look successful. Metadata parsing/accounting itself must respect the frame and metadata bounds before allocation; a TTL alone is not a capacity bound.

## Target/config and path authority

Config generation covers the original argv, cwd-relative interpretation, selected executable, resolved applicable config/Include closure and helper-relevant context. Evaluating OpenSSH configuration can execute configured Match exec or other helpers; it is not a side-effect-free parser. Do not run it on unknown configuration as a “safe probe”. ssh -G output alone does not prove a stable route, host identity or future equality. Dynamic Include globs, Match conditions, proxy/helper state, agent state and changes between read and spawn can defeat a mere file hash.

Phase 0 must demonstrate either a verified live master bound to this Session/target, or an auxiliary construction that freezes the relevant trusted configuration into an operation-owned protected snapshot with applicable semantics preserved and actual host/user/route evidence checked. Never copy private keys or secrets into such snapshots or send them to plugins. If complete binding cannot be established (including unsupported dynamic config or replacement races), allow the original interactive login but reject auxiliary effects as TARGET_UNVERIFIED/CONFIG_CHANGED. Hash-and-recheck is detection, not proof of race-free freezing. No silent re-evaluation into another host. Known-host handling remains OpenSSH's; do not weaken StrictHostKeyChecking as recovery.

Paths are {namespace_id, path:string}, not local filesystem Path values. Namespace IDs distinguish each SFTP root, Shell root and local destination. Default remote directory is under an SFTP-confirmed user root, never inferred Shell cwd or '~'. The upload root means a canonical, locally authorized dedicated directory in that verified target's SFTP namespace. It is a logical scope, not an OS jail, durable inode identity or directory-handle capability. Use server-confirmed normalization and component-aware containment under that namespace's semantics, never a raw string prefix. Reject unsupported byte filenames/namespace semantics rather than lossy-decode or guess. Shell insertion separately requires a validated mapping/context.

### Cooperative upload scope

On 2026-10-22 the user selected cooperative mode A for future MVP upload planning. The remote server/account must honor the protocol and keep the upload ancestors stable. Other programs using that account must not rename, replace, symlink or independently modify operation-owned directories/files throughout the live operation **and cleanup**. SSHX operations use separate owned resources; a competing final-name creator still must not be overwritten. This is an explicit trust precondition, not evidence that such interference can be detected or prevented. A hostile server or same-account ancestor/temp replacement is outside this mode's enforced guarantee; stronger confinement remains unsupported. [ADR 3](adr/0003-transfer-backend.md) preserves the Phase 0 general-root no-go.

Core requires existing local-user policy/consent for the actual target, namespace, canonical root and `path_scope.policy: "cooperative"`. Installation, an image trigger, a plugin manifest/request or a server report cannot supply that policy. Core's `issuer: local_user_policy` binds those values and profile/config generation into `scope_digest`, alongside immutable B. A change to policy/consent, target/config, namespace or root invalidates the affected authority; a plugin cannot refresh or broaden it. Null/inapplicable path scope grants no path effects. No additional approval service, backend or enforced-mode API is introduced.

Framing and structural method validation retain their existing errors, including `-32602` for malformed fields. Wrong channel roles remain `ROLE_DENIED`; missing/revoked required method grants remain `CAPABILITY_DENIED`. After those common role/instance/B/grant/deadline checks, a structurally valid upload with no applicable cooperative path-policy authorization, or whose required guarantee exceeds this mode, returns `PATH_DENIED` without new transfer/input effects. Never silently downgrade a stronger requirement. Unknown/changed target/config retains `TARGET_UNVERIFIED`/`CONFIG_CHANGED`; basic OpenSSH login is independent of upload eligibility.

Before creation, publication and each path-based cleanup, recheck available ancestor/type/symlink/access observations, canonical containment and quota. Reject known inconsistency, traversal and symlink substitution as `PATH_DENIED`; do not continue effects after observing a broken precondition. Portable metadata, 0700, exclusive creation and random names do not establish durable identity, atomic ancestor confinement or freedom from replacement/ABA between requests. Returned remote data remains untrusted at the local boundary even in this cooperative mode. Do not give plugins credentials, raw execution or self-grant authority.

### Future regular-PNG publication

The selected product primitive within backend B is verified `hardlink@openssh.com` **version 1**. The bounded probe now exercises it on generated Linux fixtures; this proposed v1 API is still not implemented in full. Admission requires evidence for the actual server/filesystem and regular-file operation; advertisement alone is insufficient. OpenSSH 9.2p1's baseline regular-file rename can fall back to a racy stat/rename on selected filesystem errors. Thus the historical positive baseline-rename fixture result is preserved but cannot establish universal no-clobber support. [Pinned implementation](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_2_P1/sftp-server.c) and [extension specification](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_2_P1/PROTOCOL), reviewed 2026-10-22. The [SFTP v3 draft](https://www.openssh.org/txt/draft-ietf-secsh-filexfer-02.txt) is historical, not a new standard; its filename operations supply no atomic ancestor capability.

1. Verify cooperative scope, B/grants and the required no-overwrite publication capability before data creation. Exclusively create an operation-owned private directory under the authorized root and a regular temp within it; never adopt an existing/symlinked resource. Record exact namespace/paths and acknowledged creation in Core's ledger. Verify expected type/access observations; private permissions protect against other users, not the same account.
2. Stream sealed bytes through the returned file handle with actual byte counts, bounded chunks, quotas/deadlines and per-step cancel/revoke admission. Require successful close before publication, then revalidate the scope observations and effect admission.
3. Link the completed regular temp to a new final basename in the **same operation directory/filesystem** using that verified extension. The user-visible final path includes the operation directory; no later directory rename is required. Never fall back to baseline/POSIX rename, stat-then-overwriting rename, scp or a remote command. Missing/unverified version or explicit unsupported/cross-filesystem capability failure returns `COMMIT_UNSUPPORTED`; no completed upload or temp-path insertion follows. A confirmed destination collision is `NAME_EXISTS` and preserves its bytes. Generic SFTP failures must not all be relabeled collision or unsupported capability: retain the observed I/O/uncertain outcome.
4. An acknowledged successful link sets `upload_state: committed` and `final_commit: "confirmed"`. Separate owned-temp unlink is cleanup, not a prerequisite for final commit. Failed temp cleanup leaves the committed final result and `cleanup_pending: true`; never unlink the final name to roll back. Lost/ambiguous publication acknowledgement instead yields `upload_state: indeterminate` and `final_commit: "indeterminate"`, no insertion and no automatic re-publication. Query/reconcile known resources read-only; equal size is not hash or commit proof.

The current cooperative Core probe uses hardlink; baseline `raw.rename` remains only in the explicitly historical backend comparison and its reply-loss experiment. Archived source-bound reports remain unchanged. [Current runtime evidence](phase-0.md#cooperative-runtime-checkpoint) separates actual filesystem cases from injected faults and outstanding review gates. Cooperative scope does not make an unverified commit safe.

### Owned cleanup authority

Cleanup removes only exact, acknowledged operation-owned temporary resources in the Core ledger while verified target/config/namespace, cooperative continuity and adequate ownership evidence remain live. Each removal needs a fresh bounded admission check for that exact resource. After cancel/revoke/disable, Core may use only this narrow pre-existing ledger authority for cleanup; it grants the plugin no renewed upload/publication permission. Cleanup is not an exception permitting new data or final publication.

Changed/missing/inconsistent ownership evidence, uncertain creation/commit outcome, transport loss or a new Core/generation stops automatic path-based deletion and records pending cleanup. Do not infer ownership from a matching name, size, attributes or random token; do not adopt names after reconnect, follow replacement symlinks or recursively sweep a directory. Never remove final user data, including a committed final file after insertion failure; its containing operation directory is retained. Unknown resources stay pending for explicit reconciliation rather than guessing deletion. These rules remain conditional on cooperative continuity and do not claim to defeat undetected same-account replacement.

## Roles and local IPC

Unix: protected user runtime directory, no-follow parent traversal, user-only socket permissions and native peer credential verification; check server identity too. Linux's SO_PEERCRED is a documented option; macOS needs its own native peer API and test. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), reviewed 2026-10-22.

Windows: explicit current-user and intended logon ACL, reject remote pipe clients, validate connecting process/token and server identity, do not rely on default pipe ACL or pipe name. Test alternate local users/logon sessions and endpoint squatting. Microsoft documents security descriptors and pipe access checks; actual SSHX ACL/peer behavior is unverified. [Named-pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), reviewed 2026-10-22.

Authenticated Client channels carry management/user intent, plugin stdio carries only plugin role and requested grants. Peer credentials separate local users but do not sandbox malicious same-user processes or administrators. Client UI trust is an application boundary, not proof against an already compromised account. Plugin channels cannot become Clients, self-grant permissions, attach terminals or open a raw desktop bridge. Core has no TCP management listener.

Client control IPC uses the same framed JSON-RPC as plugins. After Client hello, separate user-authenticated connections may bind single-use stream tickets to that Client/Attachment or Operation. Core issues random unguessable tickets through control IPC, expires them under FRAME_TIMEOUT, checks peer/boot/role/B again, consumes them once, then permits only that stream's data type. They are not filesystem paths or credentials usable by plugins.

Only live owners may hold stream tickets: at most two outstanding terminal tickets per Attachment and one outstanding blob ticket per Operation, no more than 2 × SESSION_MAX + OPERATION_MAX overall. Reissuing a ticket for the same purpose invalidates the prior ticket; there is at most one open stream per owner/purpose, and replacing it closes the old stream first. Consumed, expired or revoked tickets leave the pending map immediately; no used-ticket history grows beyond the owner metadata. Detach/cancel/close revokes the owner's tickets/streams. Ticket reservation and all grant/Client allocation are subject to CORE_METADATA_BUDGET_MAX before publication.

Terminal and Client blob channels use binary records: kind:u8, sequence:u64 big-endian, payload_length:u32 big-endian, followed by exactly that many bytes. Kinds are data=1, eof=2 (zero payload), error=3 (bounded UTF-8 error name); TERM_CHUNK_MAX also bounds blob channel records. Sequences start at zero per direction, increment once per record and reject gaps/repeats; blob offsets are cumulative, no seeking. Terminal input is bound to writer_epoch in its stream binding; revocation closes it. A short read is not EOF or a character boundary. All control, terminal and blob channels have independent drains/budgets. No stream admission bypasses Core quotas.

The managed terminal output gate parses OSC strings across byte reads, recognizing ESC ] and raw C1 OSC starts, BEL and ESC-backslash/raw C1 ST terminators, with a streaming UTF-8 state so continuation bytes are not confused with C1 controls. OSC 52 and 5522 are suppressed including query responses; they cannot trigger local reads/writes. Unknown OSC/control sequences pass through only under documented host behavior, never as authenticated Shell events. Malformed, oversized or unterminated control strings stop display delivery under TERM_CONTROL_MAX/TERM_CONTROL_TIMEOUT, detach the affected Client with DISPLAY_INCOMPLETE and continue draining the owned PTY. Do not flush accumulated control fragments to the host on error. Actual emulator/C1/multiplexer behavior remains E2/E6 evidence; this is a narrow proposed clipboard gate, not universal terminal sanitization. If a supported host admits another clipboard mechanism, disable that mechanism or mark the combination unsupported until gated. A restoration renderer emits only its selected safe visual state, never the original OSC strings.

## Framing and version negotiation

Content-Length: N followed by CRLF CRLF and exactly N UTF-8 bytes. Header name is ASCII case-insensitive; allow only that single header, decimal digits with no sign, and the mandatory space after colon. N must be positive and within BODY_MAX. Reject duplicate/unknown headers, bare LF, non-ASCII, invalid UTF-8, BOM, duplicate JSON keys, excessive depth, nonfinite numbers or trailing JSON content. Close channel on framing loss/timeout; never resynchronize by searching arbitrary bytes. A complete invalid JSON frame may return standard parse error with null id before closing. stdout logs are protocol violations. JSON-RPC defines objects/errors, not this framing or authorization. [JSON-RPC specification](https://www.jsonrpc.org/specification), reviewed 2026-10-22.

Only single object messages are accepted; JSON-RPC batches are an unsupported profile feature (Invalid Request). Each sender's request id is a decimal string counter starting at "1", increasing by exactly one per request on that channel/direction, bounded by INTEGER_MAX. Receiver keeps only the last admitted counter plus bounded pending requests, not an unbounded used-id set; reject repeated/out-of-order request counters, close/reconnect before exhaustion. Ids are correlation, not dedup keys. A response contains the same id and exactly one of result/error. Out-of-order responses are allowed, and counters in opposite directions are independent. Only explicitly defined notifications have no id; notification errors have no response, and protocol abuse closes the channel. Unknown methods return -32601; unknown request fields return -32602, so typos cannot broaden scope. Negotiated minor extensions can define optional fields; unknown optional fields in responses/events are ignored but cannot be interpreted as authority. Required new fields/semantics need negotiation or a major change.

Core sends plugin.initialize first with {api_versions:["1.0"], core_instance_id, core_version, manifest_digest, limits_profile:"proposed-v1"}. Plugin returns {api_version:"1.0", plugin_version, features:[]} within HANDSHAKE_TIMEOUT. Core verifies against validated manifest; no privileged requests before successful response. Core then sends plugin.ready notification {api_version:"1.0", instance_id, available_methods:[...]} and the plugin may register actions. Claimed plugin ids never select identity; Core allocated the instance from the child/channel. No common version: VERSION_MISMATCH and stop. Client hello similarly negotiates API and allocates client_id; it cannot set identity in params.

Lifecycle: discovered → validated → starting → initializing → ready → stopping → stopped/failed. Validate local package manifest before execution: {id,version,api:{min,max},entrypoint,args:[],platforms:[],config_schema:{},actions:[],capabilities:[]}. Reject absolute/traversal/duplicate archive entries, symlink/hardlink/device entries, escaped entrypoint, decompression excess, platform/API mismatch or executable outside owned package. No install hooks/scripts. Explicit trust/enable precedes start; official packages get no bypass. Spawn with minimal environment and no inherited agent/PTY/secret handles. Failure/restart is bounded by Limits, assigns a fresh instance and grants, and never auto-replays an action. Disable revokes first, cancels in-flight work, requests stop, then terminates owned plugin child after grace. Unsandboxed plugins remain capable of same-user filesystem/network access outside RPC; [ADR 5](adr/0005-plugin-isolation.md) defines that boundary.

## Effect ordering, deduplication and cancellation

Each Session has a Core serialization domain shared by attachment/epoch transitions, revocation, operation cancellation, upload commit decisions and PTY insertion admission. Before each effect, check actual channel role/instance, B, generation, current config/target, path scope, grant method/quota/deadline/revocation, operation state and effect key. Expensive streaming work runs outside the lock but rechecks before each external step. No long-running transfer holds up terminal drain.

Client action trigger_nonce is a monotone decimal string counter, not an opaque object Id. It starts at "1" for each live client_id, has no leading zeros, is bounded by INTEGER_MAX, and is independent of the RPC request-id counter. Core retains one last-admitted high-water value for that Client identity's whole lifetime. New operation creation requires exactly the next value and advances it atomically with admission; failed admission creates no effect and does not advance it. The dedup key is (core_instance_id, client_id, trigger_nonce): while its record exists, identical intent digest returns the same operation/result and conflicting intent yields DEDUP_CONFLICT. A value at or below the high-water mark whose record has expired returns EXPIRED, never creates another Operation; a skipped/new out-of-order value is Invalid params. This needs only one counter plus the bounded retained records, not an unbounded used-nonce set. Channel loss invalidates client_id; a reconnect negotiates a new identity/counter and must never automatically replay an earlier action as a new trigger. Close/reconnect before counter exhaustion. A fresh explicit user action may create a new Operation; it is not a retry guarantee for old effects.

Plugin effects have exactly one upload_key and insert_key per Operation, persisted in its in-memory effect ledger for RESULT_TTL. Upload intent digest covers sealed blob digest, directory/namespace, basename, authorized scope_digest and B. Insert intent digest covers confirmed upload result, mapped path/mapping version, output_mode, exact validated text and B. Fresh context_revision/lease and renewed narrower grant_ids are authorization evidence, excluded from the stable insert intent digest. An identical repeated call returns recorded status/result; changing stable intent with the same key fails. Only a recorded refused proposal that admitted zero bytes may be reconsidered with new authorization/context evidence; after pending/admitted/committed/partial/indeterminate, the same key only queries the recorded outcome. Never create a new operation automatically after timeout. After operation retention expiry return NOT_FOUND/EXPIRED; no transparent replay. This is bounded, same-boot dedup, not exactly-once remote delivery across Core crash.

Cancel linearizes when Core marks cancel_requested under that domain. If cancellation/revocation wins before a step is admitted, no new upload/publication/input step starts. A remote request or PTY write already in flight may finish; cancellation is not rollback. Recheck after it returns, record observed effect, prohibit subsequent insertion, and stop work. Cleanup uses only the narrow Core-owned ledger authority in [Owned cleanup authority](#owned-cleanup-authority); it does not renew plugin grants, and loss of continuity leaves cleanup pending. Cancellation returns {accepted, phase, effects_in_flight, upload_state, insert_state}, never implies that already committed remote files disappeared. Upload commit request admission is its point of no safe rollback; if acknowledgement is lost, mark upload_state indeterminate and reconcile the known owned paths read-only, never blindly re-upload/delete a possibly committed final file. Backend cancellation closes only its own auxiliary channel/child; shared master/session remains alive.

Insertion admission serializes all ordinary input with the final target/context check and one contiguous bounded insert payload. Mark insert_state pending before the write; commit on successful complete write. A partial write records partial, an unobserved completion records indeterminate, and neither is replayed. Cancel racing an admitted write reports its actual/uncertain outcome; it cannot retract bytes. A retry of the same insert_key never queues bytes twice. A refused proposal that wrote zero bytes may be reconsidered only through a fresh local context/confirmation revision on the same Operation, not a new upload. Core must not claim exactly-once interpretation by a remote application merely because the PTY write completed.

Client loss/switch/detach revokes the initiating delivery lease and cancels further operation effects. A completed upload remains a retained result; another Attachment cannot inherit its pending insertion. Reconnect invalidates B by generation. Plugin disable/restart revokes all its grants/handles and input proposals; redacted result remains accessible to the owning user through Client management. The UI may offer copy/manual use, never auto-retarget. Core reboot loses dedup/leases; unknown remote outcomes require explicit user reconciliation.

## Methods

Tables define the complete proposed implemented surface for Phase 1 unless marked reserved. Braces describe field sets, not JSON Schema files. All calls inherit framing/limits and common errors; each action with B is rechecked at the stated effect site. Default timeout is RPC_TIMEOUT; long work returns an Operation projection immediately and completes asynchronously within OPERATION_TTL and stage-specific deadlines. Timeout of a request is not automatic operation cancellation: query operation.get, never retry effects under a new key. operation.cancel remains admitted even when normal pending slots are full; reserve a control slot. Local user authorization belongs to authenticated Client UI, never a plugin reply.

## Images and result types

Snapshot representation is tightly packed, top-to-bottom, non-premultiplied RGBA8, sRGB interpretation, stride = width × 4, byte_length = stride × height. Client adapter must validate native metadata/size before conversion, reject unsupported formats/animated or malformed input, reserve budget before native read/decode where possible, and abort if the platform API cannot enforce these bounds. Core independently checks dimensions, multiplication, declared/actual length and global quota before accepting streaming bytes. It does not trust a plugin-supplied dimension or allocate unbounded decoded image. Client-native APIs that allocate before exposing metadata require their own measured limitation in E3; until bounded, that combination is unsupported. One successful snapshot is immutable; a clipboard change during upload cannot replace it.

Plugin reads that authorized raw blob and encodes static RGBA PNG while preserving alpha; this is policy/encoding in the plugin, not a Core image business service. The permitted encoder profile is signature plus IHDR (RGBA8), optional sRGB, IDAT and IEND only, with valid chunk ordering/CRC and no trailing bytes. Plugin removes other metadata before seal. Core validates exact sealed bytes, dimensions and bounded decompressed size before transfer, rejects forbidden chunks, animation and mismatched raw dimensions, and never rewrites bytes after hashing. A mature validator remains a dependency decision, not an invented API. PNG supports truecolor with an alpha channel; SSHX narrows to this static profile. [PNG specification](https://www.w3.org/TR/png-3/), reviewed 2026-10-22.

Upload result (`UploadResult`, a document type alias, not a wire wrapper) = {transfer_path:{namespace_id,path}, shell_path:{namespace_id,path}|null, mapping_id|null, size, integrity:{local_sha256,remote_verification:"readback_sha256"/"size_only"/"none",remote_sha256|null}, final_commit:"confirmed"/"indeterminate", cleanup_pending}. Operation.result is null before an upload result exists; a recorded indeterminate result uses this same shape without claiming completion. The final transfer_path includes the retained operation directory, never the temporary basename. Same size never implies hash equality. Optional bounded readback uses the same grants/budget; no remote shell checksum command is injected. No completed result is available until confirmed no-clobber publication; an indeterminate result is not insertable. Confirmed publication remains committed if temp unlink fails, with cleanup_pending true; cleanup failure alone does not retract a confirmed final path. Final file is user data and is never automatically removed on insertion failure/cancel.

Text insertion rejects NUL, ESC, CR/LF, all C0/DEL/C1 control characters; output must fit TEXT_MAX. It must not append Enter. Modes are distinct: shell_argument needs a verified Shell-specific encoder and fresh edit position (complete argument boundary, no open quote); plain_path needs a verified plain-text receiver or explicit user-confirmed paste lease; markdown needs a known document reference or absolute mapped URI/path and a validated formatter. Unknown Shell/context/mapping gets preview/copy only, never POSIX quoting by assumption. Bracketed paste is negotiated receiver behavior, not a safety sandbox. Any user input while previewing cancels the lease before forwarding; the lease never discards buffered input silently. A new output/context revision invalidates automatic insertion. No context obtainable: refuse with CONTEXT_UNKNOWN, retain result, offer copy/manual use. See the [transaction](image-paste.md) for retry rules.

## Events and errors

Core sends event notification {api_version,event_id,subscription_id,session_id,generation,operation_id|null,source:"core",sequence,kind,payload}. Ordering is per subscription, sequence starts at zero and strictly increases; cursor is the next expected sequence; no global exactly-once bus. Kinds: session.state, attachment.revoked, operation.progress, operation.result, grant.revoked, event.gap. Source remote data must carry its origin/freshness/trust inside payload and never becomes Core authority. On overflow, send event.gap {last_delivered,next_available,requery:["session.describe","operation.get"]}; discard obsolete progress and require state query. If gap cannot be delivered under bounds, disconnect subscriber/plugin and revoke its grants; PTY continues. Operation results remain queryable under RESULT_TTL even if notification delivery fails. Subscriptions end at operation/session close, channel loss or explicit cancel; no terminal/clipboard data is broadcast. plugin.ready and event are the only Core plugin notifications in this profile.

Error envelope = {code:int,message:string,data:{name,retryable,operation_id|null,phase|null}}; names below are exhaustive categories, message is metadata without secret paths/bodies. No stack trace to plugins. Standard JSON-RPC codes -32700 Parse error, -32600 Invalid Request, -32601 Method not found, -32602 Invalid params, -32603 Internal error retain their standard meaning; SSHX uses -32000 with a stable data.name for domain errors. INTERNAL_ERROR masks unexpected details and fails affected action, not main ssh.

| Names | Meaning / retry rule |
| --- | --- |
| VERSION_MISMATCH, ROLE_DENIED, CAPABILITY_DENIED | No compatible API, wrong channel role or missing/revoked permission; no automatic retry |
| LIMIT_EXCEEDED, BUSY, WRITER_BUSY | Bounded admission failure; retry only explicit status/user action, not a new effect key |
| STALE_BINDING, CONFIG_CHANGED, TARGET_UNVERIFIED | Wrong generation/Attachment/epoch/config or unverified target; cannot retarget existing operation |
| EXPIRED, CANCELLED, NOT_FOUND, DEDUP_CONFLICT | Deadline/cancel/missing boot-scoped object/conflicting same-key payload; no hidden recreation |
| TIMEOUT, IO_ERROR, UNKNOWN_DELIVERY | Stage deadline, observed I/O failure, uncertain external effect; query/reconcile, never blind repeat |
| CLIPBOARD_EMPTY, CLIPBOARD_UNAVAILABLE, CLIPBOARD_DENIED, CORRUPT_IMAGE | Explicit snapshot/validation failures; a new user action needed for new snapshot |
| AUTH_REQUIRED, NO_SFTP, UNAVAILABLE | Auxiliary interactive auth unsupported, subsystem absent, capability not implemented; login can remain usable |
| PATH_DENIED, NAME_EXISTS, COMMIT_UNSUPPORTED | Missing/inapplicable cooperative path policy, unsupported stronger-root requirement or namespace/symlink/ACL/path refusal; confirmed final collision; or no verified no-clobber publication capability respectively. Preserve common role/method-grant errors; do not classify every generic SFTP failure as collision/unsupported. Never silently overwrite |
| CONTEXT_UNKNOWN, CONTEXT_CHANGED, MAPPING_UNKNOWN | Upload may have succeeded; retain result, fresh preview/copy rather than automatic insertion |
| DISPLAY_INCOMPLETE | Output overflow or restoration gap; attachment must re-query/re-render safely |
